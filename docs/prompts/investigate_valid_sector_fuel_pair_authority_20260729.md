# Investigate and design a reusable valid sector/fuel pair authority

## Task type

Investigation and contract-design task, with an optional shadow implementation
only after the evidence and semantics are clear.

Work queue item: `MAPQ-034`.

The purpose is to determine, carefully and reproducibly, which source
sector/fuel combinations should be considered possible, relevant, or valid
across `leap_mappings` and `leap_initialisation`. The result should replace
duplicated ad hoc checks with a reusable mappings-owned contract. Do not migrate
production consumers or edit maintained mapping workbooks during this task.

## Why this needs a separate investigation

Several current workflows ask whether a sector/fuel pair "exists", but that
phrase can mean materially different things:

- structurally available in a source dataset or LEAP template;
- observed with at least one finite non-zero value;
- structurally present but zero-only in the selected scope;
- present only in another scenario, economy, year range, or data vintage;
- reviewed and intentionally reserved even though it is not currently active;
- accepted in a mapping workbook; or
- generated by independently combining a sector axis and a fuel axis, without
  evidence that the exact pair is allowed.

Do not collapse these meanings into one Boolean. A principal goal of this task
is to define their names, evidence, authority, and permitted uses.

## Primary investigation questions

### 1. What question is each existing check answering?

Build an implementation inventory covering both repositories. For every
relevant function or workflow, record:

- repository, file, and symbol;
- caller(s) and output consumer(s);
- source data and scope;
- exact pair-key construction;
- hierarchy-depth rule;
- subtotal/parent treatment;
- non-zero tolerance and when it is applied;
- scenario, economy, vintage, and year behavior;
- whether signed values can cancel before the check;
- whether the result means structure, observation, mapping acceptance, or a
  mixture;
- whether it can create an unsupported Cartesian pair;
- current tests; and
- retain, replace, wrap, or retire recommendation.

Pay particular attention to identically named or nearly identical functions
that have drifted between the repositories.

### 2. What constitutes an exact source pair?

For the Ninth Outlook, verify the correct most-specific sector and fuel
selection from:

- `sectors`, `sub1sectors`, `sub2sectors`, `sub3sectors`, `sub4sectors`; and
- `fuels`, `subfuels`.

Test blank values, `"x"`, duplicated hierarchy rows, parent rows, subtotal
rows, and conflicting populated hierarchy levels.

For LEAP, determine which evidence can prove an exact branch/fuel combination:

- per-economy model templates;
- balance/export files;
- mapping sheets;
- reviewed reserved-pair configuration; and
- any LEAP API or export metadata already used by the repositories.

Explicitly test whether the prior template inventory proves exact branch/fuel
membership or only branch structure. Never create a global LEAP pair registry
by taking the Cartesian product of independently observed branches and fuels.
A pair absent in one economy must not be declared globally invalid when other
economies or templates support it.

For ESTO, treat flow/product as the analogous two-axis pair so the reusable
design is not narrowly hard-coded to Ninth column names.

### 3. What are the evidence and authority states?

Propose a small, explicit state model. It should be able to distinguish at
least:

- structurally present;
- observed non-zero;
- observed zero-only;
- absent in the inspected scope;
- reviewed/reserved;
- pending confirmation after a vintage change;
- dormant, if a dormancy policy is eventually approved; and
- rejected/invalid with a recorded reason.

Also distinguish generated evidence from accepted authority. Decide whether a
single status plus evidence columns or several orthogonal fields is clearer.
Do not silently implement a dormancy threshold; the separate-axis exploration
found insufficient vintage history to establish one.

### 4. Which scope controls validity?

Measure and explain the effect of:

- reference, target, and all-scenario union for Ninth;
- individual economy and cross-economy union;
- current accounts versus projection years;
- full available horizon versus selected workflow years;
- current and prior ESTO vintages;
- current LEAP templates versus partial observed exports; and
- leaf-only versus subtotal-inclusive scopes.

Recommend defaults per use case rather than one universal default. For
example, mapping availability may require a scenario union while a
scenario-specific QA check should retain separate status.

### 5. Is the non-zero rule technically valid?

Validate the prototype rule that a pair is observed-active when at least one
finite source cell has absolute value greater than `1e-9`. Test:

- positive, negative, and very small values;
- signed cancellation across rows or years;
- `NaN`, infinity, blanks, strings, and source missing-value markers;
- duplicate rows;
- all-zero structural rows;
- a pair active in only one economy, year, or scenario;
- parent/subtotal rows that duplicate children;
- values removed by workflow-specific filters; and
- the difference between testing before and after aggregation.

The registry should preserve useful support evidence such as active economies,
years, scenarios, row counts, non-zero cell counts, and absolute magnitude.
Do not use total signed sum alone as the existence test.

### 6. How reliable is the proposed authority?

Use several independent checks:

- differential comparison with the separate-axis prototype;
- differential comparison among current production implementations;
- hand inspection of stratified examples from every status and disagreement
  family;
- coverage of reviewed active mapping source and target pairs;
- false-positive review for unsupported axis cross-products;
- false-negative review for reserved, future, aggregate, and economy-specific
  pairs;
- hierarchy and subtotal checks;
- current-versus-prior vintage deltas;
- current-scenario versus scenario-union deltas; and
- downstream read-only smoke checks in mapping-candidate generation,
  source-parent validation, projections, conservation, and seed/template
  validation.

Mapping workbook membership is review evidence, not proof that a pair exists in
source data. Conversely, lack of a current non-zero observation is not enough
to delete an accepted mapping.

### 7. What should be reusable?

Design the smallest useful mappings-owned interface. Evaluate whether it
should provide:

- one generic pair-registry builder with dataset adapters;
- a shared exact-pair/hierarchy normalizer;
- versioned generated snapshots;
- a reviewed overlay for reserved/rejected decisions;
- a compiler that produces an accepted registry;
- snapshot-delta tooling;
- a manifest with source path, vintage, scope, fingerprints, tolerance, and
  row counts; and
- narrow consumer views for Ninth, ESTO, and LEAP.

Avoid a speculative framework. Prefer simple functions and tables with explicit
parameters. Keep structural availability, observed activity, and review
authority separate even if convenience views combine them for a named use
case.

Do not make `leap_initialisation` import code from a sibling checkout. Propose a
versioned artifact or another stable boundary that works in clean,
independently checked-out repositories.

## Decision and stop conditions

Stop and request a human decision before:

- choosing a dormancy duration;
- treating zero-only as invalid for all uses;
- treating mapping membership as structural authority;
- defining a reviewed reserved-pair or rejected-pair policy;
- changing the scenario-union default;
- moving or deleting an existing implementation whose callers are not fully
  known;
- editing `outlook_mappings_master.xlsx` or any other maintained workbook;
- writing a generated registry into `config/`;
- changing production pipeline behavior;
- editing production code in `leap_initialisation`; or
- accepting a design that cannot distinguish structure, observation, and
  review authority.

If exact LEAP branch/fuel structural evidence cannot be obtained from current
templates or exports, record that limitation explicitly. Do not substitute a
Cartesian estimate and call it authoritative.
